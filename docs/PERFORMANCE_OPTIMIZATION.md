# 启动吞吐与稳定性优化（2026-10-18）

本轮保留每个UV独立启动、关闭Chrome，保留UA、CPU核心数、内存、视口、代理及会话隔离。没有启用浏览器进程池，也没有修改用户保存的任务并发、投递间隔、页面等待和IP有效期配置。

## 实现

- 主进程及启动时已有子进程仍先绑定Windows Job。只把查询进程所用的诊断CDP断开放到页面准备的并行路径；观察器最多等2秒，记录异常并观察迟到失败，UV清理结束前收回观察器。浏览器退出仍确认所属主进程及子进程已退出。
- 每次启动仍使用新进程快照，避免旧快照漏掉已经创建的子进程。先建立父子索引，再遍历所属子树，将反复遍历全机进程的查找改为线性遍历。保留进程创建时间检查及PID归属边界。
- 使用已有的每秒系统采样保护启动准备，不在热路径重新采样。CPU趋势达到80%时额度降至配置的一半、至少1路，达到93%降至1路；回落后恢复。物理/提交余量取较小值，预留768MiB后，以256MiB为每路启动预算缩减额度，低于1GiB时暂缓新启动。预算是启发式保护，不能保证任意页面的内存峰值。
- 资源等待按进入队列顺序放行，可被停止/IP到期取消。保护只推迟新的Chrome启动，不取消已运行UV，也不改变已领取任务按间隔投递的规则。界面的任务领取背压开关仍独立生效。
- 启动/清理日志及调度诊断增加当前资源启动额度；0表示正在等待内存余量。辅助阶段使用独立计时，计时记录支持并发写入，导出结果增加Chrome主进程PID。
- 后续PV刷新与首次访问一致，等待DOMContentLoaded，不再等待所有子资源的load。首次页面内容检查使用剩余导航预算，避免CPU繁忙时固定2秒的控制通道等待提前判失败。原有导航超时后对已提交页面的最多2秒检查保持不变，结束时的内容/网络错误检查保持不变。

没有拆开启动与页面初始化的总名额：本机实测资源紧张时，增加同时处于初始化阶段的Chrome会影响已经打开页面的控制请求。本轮先保留这层保护。

## 验证方法

```powershell
dotnet build src/MainClient/MainClient.csproj -c Release
$env:TRAFFICVISTA_TEST_CHROME = '本机Chrome的完整路径'
dotnet run --project src/MainClient/MainClient.csproj -c Release -- --admission-test
dotnet run --project src/MainClient/MainClient.csproj -c Release -- --reliability-test
dotnet run --project src/MainClient/MainClient.csproj -c Release -- --browser-close-test
dotnet run --project src/MainClient/MainClient.csproj -c Release -- --throughput-benchmark
```

`--throughput-benchmark`使用隐藏模式测试任务并发1/2，每项任务12个UV、2秒投递、DOM后10秒等待、导航超时20秒，每组160秒取消期限。使用本地页面、内存设备及无代理提供器，不访问正式任务接口、不领取真实IP。每档记录成功/失败UV数量、P95、各阶段耗时和成功UV/分钟，确认所属Chrome进程清零，并等待驱动关闭请求排空。不能仅根据任务成功或测试进程退出码判断全部UV成功，应检查`allUvsSucceeded`及UV计数。

`--reliability-test`增加3个并发UV的真实Chrome验证：主进程PID不同、Cookie/存储隔离、页面脚本首读的UA/CPU核心数/内存正确、进程与后台辅助阶段清零。原有测试中“部分UV成功仍算任务失败”的旧断言与当前业务语义不符，已改成至少一个UV成功的现行语义，并保留成功/失败UV数量断言。

旧`--benchmark`此前各档只是修改配置，仍投递同一个8UV任务，不能表示任务并行度。现在改成以真实任务并行度1/2/4/8执行8个单UV任务；新旧档位数据不应直接比较。

## 本机初始证据与限制

机器为Intel i3-8100、4个逻辑处理器、约32GiB物理内存。测试期间有其他应用运行，多次观察到CPU接近100%，没有关闭或清理其他应用的Chrome进程。

修改前的第一档：12个UV成功9个、失败3个，任务耗时约56.46秒，成功吞吐约9.56 UV/分钟。失败均为结束时页面内容检查的控制通道等待超时；所属进程已回收。原基准遇到UV失败后中止，未产生第二档数据。原始任务摘要和逐UV结果保存在`validation/2026-10-18/throughput/before-*.json`。

中间版本：单任务12/12成功，约50.44秒；双任务23/24成功，约98.49秒。双任务仍有一次首次页面内容检查超过固定2秒，因此最终版本继续修正该检查的预算，并补齐启动资源队列的顺序保证。中间结果仅用于记录问题定位，不能当作最终验收结果。

最终隐藏模式本地基准：

| 版本/任务并发 | 成功UV/计划UV | 耗时 | 成功UV/分钟 | UV P95 | 峰值浏览器 |
| --- | --- | --- | --- | --- | --- |
| 修改前/1 | 9/12 | 56.46秒 | 9.56 | 未采集整体分位数 | 未采集 |
| 最终版本/1 | 12/12 | 44.46秒 | 16.20 | 22.16秒 | 5 |
| 最终版本/2 | 24/24 | 89.31秒 | 16.12 | 64.25秒 | 6 |

最终版本两档均无UV失败或取消，全部所属Chrome进程归零，驱动关闭请求排空。双任务吞吐没有比单任务继续提高，且UV排队时间增加；在本机当时负载下，继续增大任务并发缺少吞吐收益证据。

`--admission-test`、`--reliability-test`、`--browser-close-test`均通过。覆盖CPU额度收敛/恢复、内存等待/取消、启动资源队列顺序、并发独立PID/UA/核心数/内存、Cookie/存储隔离、手动关闭、导航取消、供应商到期、正常关闭与进程回收。构建输出到`src/Build/MainClient.exe`，用户配置文件以构建前后哈希验证未被覆盖。

最终验证记录保存在`validation/2026-10-18/throughput/`，原始指标见`final-throughput.json`，测试报告与构建日志同目录。本地静态页面、少量任务和当时的系统负载不能推出正式代理/网站的最大任务并发，也不能保证长时间运行的固定提速比例。资源启动保护减少突发争用，但不是全局运行中浏览器数量硬上限；真实页面的脚本、视频、代理速度和停留时间仍决定容量。
